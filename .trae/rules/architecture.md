# 架构设计规范

## 1. 核心设计原则

### 1.1 分层架构
- **核心层 (core)**：包含应用的核心基础设施，如导航、主题等
- **功能层 (feature)**：按业务功能划分模块，如首页、学习中心等
- **共享层 (shared)**：包含跨模块共享的代码，如工具类、通用组件等

### 1.2 关注点分离
- **UI 层**：Compose UI 组件，负责界面展示
- **ViewModel 层**：状态管理和业务逻辑
- **数据层**：数据获取和存储
- **领域层**：核心业务逻辑

### 1.3 模块化设计
- 每个功能模块独立成一个子目录
- 模块内部按职责进一步分离
- 模块间通过明确的接口进行通信

## 2. 架构模式

### 2.1 推荐架构
- **MVVM (Model-View-ViewModel)**：适用于 UI 相关功能
- **Clean Architecture**：适用于复杂业务逻辑

### 2.2 数据流向
- **单向数据流**：UI → ViewModel → 数据层 → ViewModel → UI
- **状态管理**：使用 Compose 的 `remember`、`mutableStateOf` 或第三方状态管理库

## 3. 依赖管理

### 3.1 依赖注入
- 对于简单场景，使用手动依赖注入
- 对于复杂场景，考虑使用 Koin 或 Hilt

### 3.2 模块依赖
- 核心层不依赖功能层
- 功能层可以依赖核心层和共享层
- 共享层不依赖其他层

## 4. 平台处理

### 4.1 平台特定代码
- 使用 KMP 的 `expect/actual` 机制处理平台差异
- 平台特定代码放在对应的平台目录中
- 平台通用代码放在 commonMain 中

### 4.2 兼容性
- 考虑不同平台的特性和限制
- 确保在所有目标平台上的一致性体验

## 5. 扩展性考虑

### 5.1 未来功能扩展
- 新增功能应在 feature 目录下创建对应模块
- 遵循现有的目录结构和命名规范
- 确保新功能与现有架构兼容

### 5.2 技术栈扩展
- 引入新技术时应考虑跨平台兼容性
- 评估新技术对构建时间和运行性能的影响
- 确保团队成员对新技术有足够的了解
